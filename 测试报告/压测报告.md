# 压测报告：v1.4.1 复测（2026-10-02）

- **测试对象**：本地 `cargo build --release` 重编的 `sms.exe`（458,752 B，静态 CRT 构建，
  `.cargo/config.toml` 生效，仅依赖系统 DLL），`--server` 模式。
- **测试机**：i9-13900HX（24 核 32 线程）/ 16 GB / Windows 11 build 26300 /
  Node.js v24.20.0。
- **测试方式**：本地回环（服务端与压测客户端同机）。每轮在独立临时目录启动全新服务，
  500 条种子数据，跑完即销毁，不碰仓库里的 `students.txt`。
  压测客户端每个请求新建一条 TCP 连接并带 `Connection: close`，与服务端
  "一次连接一个请求"的处理方式一致。响应码 404（删除/修改不存在的学号）和
  409（学号重复）是负载配方里的预期结果，不算错误。
- **前置验证**：`cargo test` 全量通过（压测时 22/22；后新增 2 个原子性测试，现为 24/24）。

## 一、总体结果

| 指标 | 500 条种子 / 1 worker | 2363 条 / 2 workers | 4599 条 / 1 worker | 4599 条 / 2 workers |
| --- | --- | --- | --- | --- |
| 吞吐（8 客户端 × 15 s） | **793 请求/秒** | 685.7 请求/秒 | 348.1 请求/秒 | 664.9 请求/秒 |
| 延迟 p50 / p95 / p99 | 7.8 / 13.2 / 19.2 ms | 9.1 / 16.6 / 71.6 ms | 18.6 / 33.9 / 199.7 ms | 8.8 / 15.8 / 77.7 ms |
| 最大延迟 | 822.4 ms | 600.9 ms | 661.1 ms | 1155.5 ms |
| 真实网络错误 | **0** | **0** | **0** | **0** |
| 总请求数 / 状态码分布 | 11898（200:7778 / 201:2328 / 404:1792） | 10293（200:6248 / 201:2024 / 404:2021） | 5228（200:3114 / 201:1068 / 404:1046） | 9987（200:6045 / 201:1962 / 404:1960） |

各轮均无预期外状态码（只有 200/201/404，符合"40% 查列表 / 20% 搜索 / 20% 新增 /
10% 改分 / 10% 删除"的配方）。

## 二、边界与容错（与 C++ 版及 Rust v1.4.0 历史报告逐项对照）

| 项目 | 本次实测 | 历史报告 | 结论 |
| --- | --- | --- | --- |
| 120 连接瞬时突发 | **66 成功 / 54 被重置**，123 ms 内结束 | 65/55（C++ v1.3fix 复测）、66/54（v1.4.0） | ✅ 一致（排队上限 64 的有意背压） |
| 5 个空闲连接占用（2 workers） | 19.8 s 后返回 200 | 19.5 s | ✅ 一致 |
| 半截请求（声称 500 字节 body 不发） | 10.0 s 后 `400 Bad Request` | 10 s 后 400 | ✅ 一致 |
| 畸形请求 | 1.5 MB 超大请求头被断开、非 JSON body 400、PATCH 405、不存在路径 404 | 同左 | ✅ 符合接口约定 |
| `taskkill -9` 写负载中强杀 | 4827 行 / 4827 唯一学号 / **0 坏行**；强杀瞬间仅 4 个在途连接被重置，其余 2479 个请求全部正常完成 | 同左 | ✅ 原子落盘有效 |
| 重启后 接口条数 = 文件行数 | 4827 = 4827，POST 201 可继续写，孤儿 `.tmp` 被自动回收 | 同左 | ✅ |
| 进程资源（1 worker） | 5 线程 / 5.52 MB | 5 线程 / 4.75~6.68 MB | ✅ 一致 |

强杀后 `students.txt.tmp` 有残留——这是已知小瑕疵（专项 B 记录过）：被杀在
`save()` 中途时会留下孤儿 `.tmp`，它从不被读取，下次保存原地截断复用，最多一个、
会自愈，不影响数据。

## 三、写入路径随数据量扩展（写放大）

每个变更都全量重写数据文件并 `sync_all()`（与 C++ 版同一设计）。三轮同配方对比
可见吞吐随数据量下降，`--threads 2` 只能部分掩盖：

| 数据量 | 1 worker | 2 workers |
| --- | --- | --- |
| ~500 条 | 793 请求/秒 | — |
| 2363 条 | — | 685.7 请求/秒 |
| 4599 条 | 348.1 请求/秒 | 664.9 请求/秒 |

2 worker 在 4599 条时几乎是 1 worker 的 1.9 倍：多个 worker 可以让某个线程
在别人 fsync 时继续处理读请求。对本项目"本机单人使用"定位，默认 1 worker 够用；
多人同时高强度使用时应调大排队上限、缩短单连接超时、增加 worker 数。

## 四、吞吐差异说明

本轮 500 条种子的 793 请求/秒比 v1.4.0 历史报告（1101.9 请求/秒）低约 28%，
各轮最大延迟在 0.5~1.2 s 量级，指向本机偶发停顿（杀毒实时扫描 / 线程调度），
非程序回归——本轮各轮真实网络错误全部为 0，全部边界项与正确性结论和历史报告
逐项吻合。同机回环的吞吐绝对值相对真实局域网偏乐观，但配置间相对比较
（1 worker vs 2 worker、写放大趋势）不受影响。

## 五、结论

1. 正确性没有问题：9 阶段 + 强杀全程无 panic、无退出码异常、无数据损坏、
   无响应错乱；重启后接口与文件始终一致。
2. 常规使用性能充裕：页面刷新、增删改都是个位数毫秒级；压到约 800 请求/秒
   仍零错误；数据量过万后写放大明显，属与 C++ 版同源的设计取舍。
3. 两处设计取舍（不是缺陷）：瞬时并发超过约 66 个连接时多出的连接被快速断开；
   连上不发数据的连接占用 worker 10 秒。
