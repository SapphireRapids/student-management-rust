# 原子测试报告：原子落盘专项（2026-10-02）

- **测试对象**：`src/store.rs` 的原子落盘（先写 `students.txt.tmp` 并 `sync_all()`，
  再 `fs::rename` 原子替换）。
- **新增测试**：`tests/save_atomicity.rs`，两个集成测试，真实进程 + 真实 HTTP，不 mock。
- **全量结果**：`cargo test` **24/24 通过**（13 单元 + 5 api_json + 4 console_race +
  2 save_atomicity）；`cargo test --test save_atomicity` 并行 11.9 s、三连跑稳定。

## 一、两个用例在测什么

**1. `every_snapshot_under_write_load_is_complete`（写负载下每个快照都完整）**
1500 条种子数据、4 个客户端持续 POST/PUT，同时一个读取器以最快速度不停读
`students.txt`，**每一份快照必须整体可解析**：完整 UTF-8、每行三字段
（学号,姓名,总分）、总分是数字、学号不重复。rename 是原子的，读取器只可能拿到
旧文件或新文件，不可能拿到写了一半的——这就是断言的核心。
收尾再核对接口条数 = 文件行数、无残留 `.tmp`。

**2. `kill_during_write_never_corrupts_the_file`（强杀不损坏文件）**
3000 条种子，5 轮"写 700 ms → `kill()`（Windows 上等价 `taskkill -9`）"，
读取器跨越全部轮次持续盯着；每轮强杀后文件必须完整可解析、唯一学号数不少于种子数；
重启后接口条数 = 文件行数、可继续写、孤儿 `.tmp` 不残留。

配套的工程细节：`Server` 类型带 `Drop`，测试进程退出（含断言失败 panic）时
一定回收服务端子进程；`http()` 对连接错误返回 `None` 按预期容错，不 panic。

## 二、威慑力验证（突变测试）

把 `save()` 从"先写 `.tmp` 再 rename"退回旧写法（`File::create` 直写原文件）：

```
test every_snapshot_under_write_load_is_complete ... FAILED
test kill_during_write_never_corrupts_the_file    ... FAILED
test result: FAILED. 0 passed; 2 failed; ... finished in 7.61s
```

两个用例 7.6 秒内双红——读取器在第一次写盘进行中即读到被 `File::create`
截断成空/半截的文件。恢复原写法后全绿。

## 三、排障记录（写这套测试时发现并修掉的问题）

1. **测试自身缺陷一：并行干扰**。两个用例原先共用同一对 `static STOP/STOP_READER`
   停止标记，cargo 默认并行跑用例，测试一结束时会置位停止标记，把测试二的写负载和
   读取器提前掐断，测试二可能"空转通过"。已改为每个用例私有的 `Arc<AtomicUsize>`。
2. **测试自身缺陷二：假通过**。`http()` 原先在连接被重置时 `unwrap()` 直接 panic，
   写线程静默死亡——强杀用例在旧写法下因此"假通过"。已改为返回 `None` 按预期容错。
3. **Windows 回环连接的冷启动延迟（内核行为，非本程序缺陷）**。服务端刚被 kill 后，
   客户端再向该端口 `connect()`，SYN 会被静默重传约 0.5/1/2/4 秒才收到 RST
   （读已建连接则是毫秒级失败）。测试改用 `connect_timeout(500ms)` 避免 join
   写线程时干等，`save_atomicity` 并行耗时 25.3 s → 11.9 s。
   网页前端在服务端消失后重连同样会感受到这个延迟，属系统层行为。

## 四、结论

1. "先写 `.tmp` 再 rename"的原子落盘保证属实：写负载+强杀全程每份快照都完整，
   文件零损坏、零截断、零重复学号，接口与文件始终一致。
2. 该保证现在有两个回归测试背书，且对"退回旧写法"敏感（7.6 s 双红）。
3. 已知小瑕疵（与 C++ 版同源）：被杀在 `save()` 中途会留下孤儿 `students.txt.tmp`，
   从不被读取、下次保存原地复用、最多一个、会自愈，不影响数据。
